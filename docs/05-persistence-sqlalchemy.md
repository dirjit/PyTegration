# Module 5 — Persistence with SQLAlchemy 2.0 & Alembic

> **Goal:** map objects to tables, manage a unit of work, and version your schema
> — the Hibernate/JPA + Flyway story for Python.

## ORM models

See [`db/models.py`](../src/pytegration/db/models.py). SQLAlchemy 2.0 uses typed
`Mapped[...]` columns:

```python
class TaskORM(Base):
    __tablename__ = "tasks"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200), nullable=False)
    description: Mapped[str | None] = mapped_column(String(2000))   # nullable
```

| SQLAlchemy | JPA/Hibernate |
|------------|---------------|
| `class TaskORM(Base)` | `@Entity class Task` |
| `__tablename__` | `@Table(name=...)` |
| `Mapped[int] = mapped_column(...)` | `@Column private int ...` |
| `AsyncSession` | `EntityManager` |
| `Base.metadata` | the persistence metamodel |

The `Mapped[]` annotation means mypy understands your columns — `task.title` is
typed `str`, `task.description` is `str | None`.

## The session = the unit of work

An `AsyncSession` is a short-lived transaction scope (an `EntityManager`). We open
**one per request** and commit/rollback at the request boundary — see the async
generator in [`db/session.py`](../src/pytegration/db/session.py):

```python
async with session_factory() as session:
    try:
        yield session
        await session.commit()      # success → commit the whole request
    except Exception:
        await session.rollback()    # any failure → roll everything back
        raise
```

This centralizes transaction handling, exactly like Spring's `@Transactional`
around a method — but explicit and visible. Repositories therefore never commit;
they just `add`/`flush`. See
[`repositories/task_repository.py`](../src/pytegration/repositories/task_repository.py).

`flush` sends pending SQL **now** (to get generated ids/defaults) without ending
the transaction; `commit` makes it durable.

## Queries (2.0 style)

```python
stmt = select(TaskORM).where(TaskORM.status == status).limit(limit).offset(offset)
rows = (await session.scalars(stmt)).all()
```

Declarative, composable, and type-checked.

## Migrations with Alembic (≈ Flyway/Liquibase)

Schema changes are versioned scripts in [`migrations/versions/`](../migrations/versions).
Alembic is wired to read the app's settings and ORM metadata
([`migrations/env.py`](../migrations/env.py)), so it can **autogenerate** a draft
migration by diffing your models against the live schema:

```bash
alembic revision --autogenerate -m "add due_date to tasks"
# READ the generated file, adjust if needed, then:
alembic upgrade head      # apply
alembic downgrade -1      # revert one step
```

**Always review autogenerated migrations** — they're a smart draft, not an oracle
(they can miss renames and data backfills).
